## 1. 目标与路线

保留原机 Android 5.1.1 及晶晨驱动，移除大麦桌面、商城、广告、推送、旧视频和更新应用；开机自动进入第三方 B 站客户端，按 HOME 回 FLauncher，设置入口打开安卓原生设置。保留乐播投屏、遥控和必要控制组件，补齐校时、现代根证书、浏览器、输入法及可管理的永久 root。

## 5. 首次获取 root：原机到永久权限的实际路线

### 5.1 授权边界

本次实机研究在设备所有者授权下进行了临时提权、永久 root、ADB 安全配置以及“所有通过已授权 ADB 连接进入的 shell（UID 2000）获得永久 root；其他应用由管理器弹窗决定”。设备所有权与这一具体授权已确认。其他设备应重新核对型号、状态和所有者意图。

不要把网络 ADB 当作互联网服务公开。私钥、账户 Cookie、用户数据和 APK 签名私钥没有放入公开仓库源码。

### 5.2 原厂 Binder 服务提供了临时入口

原系统有 root 进程及 Binder 服务：

```text
rootserver.root_flinger
descriptor: com.hiveview.root.IRootFlinger
```

实机确认接口：1 是 chmod，2 是 chown，3 是 silentInstall，4 是 rmTool，5 是 ping，6/7 是 printk 控制。

这里的路径参数是 native `CString`，不是 `s16`。把 UTF-8 路径加 NUL、补齐 4 字节，按 little-endian signed int32 拆成一组 `i32`。权限参数接受 signed int 后转成 16 位；例如 04750 可用 `04750 - 65536` 表达。仓库源码中 `scripts/device.py` 的 `cstring()`/`binder()` 留存了编码方法。

临时助手是仓库源码 `root-helper.S`，由 `build_root_helper.py` 使用 Apple clang 的 ARM 汇编目标构建成 175 字节 ARM ELF。它仅执行 setgid(0)、setuid(0)、再 exec `/system/bin/sh`，不是联网 root 服务。

操作原理：短暂允许 ADB shell 在 `/mnt/asec` 放置该文件，随后恢复目录原 owner/mode；助手 owner 为 root、group 为 shell、mode 04750，路径 `/mnt/asec/dm4036-root-sh`。`/mnt/asec` 是允许 SUID 的内存挂载，重启消失。仅 UID 0 和 shell 组可执行。所有目录的原始权限都应先记录并恢复。

`/data` 是 `nosuid`，把 SUID 文件放在 `/data/local/tmp` 不会得到同样结果。原机临时助手得到 UID 0 后仍只继承有限 capabilities，不能把 `id` 显示 root 当作拥有 CAP_SYS_ADMIN/CAP_SYS_TIME。

仓库源码是本次步骤的参考，不是可在任意机器直接重跑的一键工具。`scripts/device.py` 的 `root` 默认走已安装的 `su`；首次提权时不能直接调用其维护阶段 root 包装器。临时阶段可明确执行以下流程（先构建 `root-helper`，并核对 `/mnt/asec` 原属性确为本机记录）：

```python
import device
# device.ADB / DEVICE / 5038 端口须先改为当前环境；只对获授权的原机执行。
device.binder(2, '/mnt/asec', 2000, 1000)
try:
    device.adb('push', str(device.ROOT_HELPER), '/data/local/tmp/dm-root-helper')
    device.shell('/system/bin/cp /data/local/tmp/dm-root-helper /mnt/asec/dm4036-root-sh')
    device.binder(2, '/mnt/asec/dm4036-root-sh', 0, 2000)
    device.binder(1, '/mnt/asec/dm4036-root-sh', 0o4750 - 65536)
finally:
    device.binder(2, '/mnt/asec', 0, 1000)
print(device.shell("/mnt/asec/dm4036-root-sh -c '/system/bin/id'"))
```

### 5.3 一次性取得完整 capabilities

本次确认：有限 UID 0 可写 root-owned 的 `/proc/sys/kernel/modprobe`。在所有者授权下，临时把它指向一个受控安装脚本，再执行 4 字节 `0xff` 的未知格式文件，触发内核 usermodehelper。安装脚本以完整 capabilities 运行。

关键约束：先记录原值；本机原值为 `/sbin/modprobe`。脚本第一行立即恢复原值，主控端也恢复并复核；安装结束删除无效文件和一次性脚本。仓库源码的 `full-root-proof.sh` 展示了恢复和 capability 检查。完整 root 的实测 CapEff 为 `0000001fffffffff`。

这是本机旧内核/原厂服务组合的实测路径，不保证其他固件可用。脚本要使用绝对路径或明确设置 PATH；SUID 启动的 shell 可能清理环境。不要执行来路不明的一键 root APK。

### 5.4 持久化方式

原机 `/init.rc` 已定义：

```text
service flash_recovery /system/bin/install-recovery.sh
    class main
    seclabel u:r:install_recovery:s0
    oneshot
```

因此无需修改 boot 分区。本次利用该既有启动钩子放置 root 启动脚本。

最终 Magisk 文件布局：

```text
/system/bin/magisk                       # 官方 v23 的 ARM32 原生二进制
/system/xbin/su -> ../bin/magisk          # 应用实际调用的 su
/system/bin/install-recovery.sh          # 开机钩子，内容见仓库源码 root-start.sh
/data/adb/magisk.db                      # 授权数据库，root:root 0600
/system/priv-app/DMBoxHelper/DMBoxHelper.apk
```

原生二进制来自官方 v23 APK 的 `lib/armeabi-v7a/libmagisk32.so`，本次 104204 字节。复制为 `magisk` 并 chmod 0755。管理器 APK 必须配套同一版本；只装管理器图标不会产生真实的权限管理。

为什么放 `/system/bin/magisk`：v23 源码 `restore_tmpcon()` 对 `/system/bin` 有 emulator 兼容特例；放 `/system/xbin` 会把所在目录 chmod 0700，导致 ADB 无法运行其中工具。本机 SELinux 原本即 Disabled，不靠修改启动分区安装新策略。

另一个坑：daemon 会校验客户端 `/proc/PID/exe` 的 inode。不能 daemon 从 `/system/xbin/magisk` 启动，而 su 指向另一个复制在 `/system/bin/magisk` 的文件。二进制内容相同仍会被拒绝。统一启动与客户端路径后重启，是本次采用的恢复方法；不要在 su 子进程里杀掉它的父 daemon 再指望后续命令可靠执行。

### 5.5 ADB 与应用授权

保持：

```text
ro.adb.secure=1
ro.secure=1
ro.debuggable=0
```

保留现有授权公钥，再加入操作电脑 的 ADB 公钥；不要覆盖其他合法 key，不要在文档/仓库源码中分发私钥。`/data/misc/adb` 为 system:shell 02750，`adb_keys` 为 system:shell 0640。

本机 ADB shell 授权记录：

```sql
INSERT OR REPLACE INTO policies
(uid, package_name, policy, until, logging, notification)
VALUES (2000, 'com.android.shell', 2, 0, 1, 1);
```

通过 root 执行官方接口：

```sh
/system/bin/magisk --sqlite 'SELECT * FROM policies;'
```

**不要省略 `package_name`。** v23 的 SQL 输出路径处理 NULL 不可靠；本次曾因这列为 NULL 导致查询中断/服务退出，补齐后恢复。2 是允许，1 是拒绝。不要为了方便把所有应用写成允许。

其他应用第一次调用 su，由 Magisk 弹窗决定；本次把管理器偏好 `su_request_timeout` 从 10 秒延长为 60 秒，原偏好另有备份，避免远距离操作时超时。永久拒绝后不会重复询问，需在管理器里修改对应应用记录。助手的“测试 ROOT 授权”只执行 `id`，校时和开机启动本身不依赖给助手应用授予 root。

本次还保留了仅接受 UID 0/2000 的本地 Java root 兜底：`RootDaemon`、`dmbox-su`，无 TCP 监听。它不是常规应用 su；常规应用使用 Magisk 的 `/system/xbin/su`。原厂 rootserver/旧内核并未做安全补丁，管理器对常规 su 的授权不能消除其他厂商提权入口；不要因此承诺达到现代 Android 的安全水平。以后若移除兜底，应先确认重启后的 Magisk 和完整恢复方案。

## 6. 时间、时区和证书

原机曾开机回到 2015 年，旧大麦授时失效。时间错误会使 HTTPS 证书看起来未生效或过期，也会影响 B 站接口。

```sh
adb shell su -c 'settings put global ntp_server ntp.aliyun.com'
adb shell su -c 'settings put global auto_time 1'
adb shell su -c 'settings put global auto_time_zone 0'
adb shell su -c 'setprop persist.sys.timezone Asia/Shanghai'
```

仅设置 `ntp_server` 不足以修复这份厂商固件。因此安装系统特权助手，声明 `SET_TIME`、`SET_TIME_ZONE`、`INTERNET`、`RECEIVE_BOOT_COMPLETED`，通过 AlarmManager 校时。

助手优先查询 `ntp.aliyun.com` / `ntp1.aliyun.com`，验证 NTP 回复来源、模式、stratum 和时间范围。开机等待网络并重试；每 6 小时再校时。仅在 UDP NTP 失败时，使用百度与腾讯 HTTP Date 双服务器结果交叉核对作为时钟引导兜底；不关闭 HTTPS 校验。HTTP/NTP 此处均不属于加密认证授时。实机最终验证成功的是阿里云 NTP 路径。

查看状态：

```sh
adb shell su -c 'cat /data/data/local.dmbox.helper/shared_prefs/state.xml'
adb shell su -c 'cat /data/local/dm4036-boot.log'
adb shell su -c 'logcat -d -s DMBoxHelper:I'
```

证书原库存有 162 个根证书，缺 ISRG/GTS 等现代根。备份原库后，补入从 CA 官方站点获取、经 OpenSSL 解析/有效期核验的 PEM，重叠证书留有逐文件备份。本次补入/更新共 23 个文件，并未用“信任所有证书”绕过验证。

来源：[Let's Encrypt 证书](https://letsencrypt.org/certificates/)、[ISRG X1 PEM](https://letsencrypt.org/certs/isrgrootx1.pem)、[ISRG X2 PEM](https://letsencrypt.org/certs/isrg-root-x2.pem)、[Google PKI roots.pem](https://pki.goog/roots.pem)。命名遵循 [AOSP cacerts 说明](https://android.googlesource.com/platform/system/ca-certificates/+/refs/heads/main/README.cacerts)：

```sh
openssl x509 -in root.pem -noout -subject_hash_old
# 以输出 hash 命名为 hash.0；出现同 hash 不同证书时须用 .1 等避免冲突
```

安装到 `/system/etc/security/cacerts`，root:root 0644，系统分区收尾恢复只读。仓库源码含本次实际证书文件。

实机使用 Android 默认 HttpsURLConnection、未自定义 TrustManager，验证：

- `api.bilibili.com`：TLS_OK，HTTP 301。
- `cat3399.top`：TLS_OK，HTTP 404（路径不存在不影响 TLS 成功）。
- `valid-isrgrootx1.letsencrypt.org`：TLS_OK，HTTP 200。

测试代码为仓库源码 `TlsCheck.java`。证书补齐不能使 Android 5 的全部 TLS/浏览器能力等同现代系统。

## 8. 恢复原生设置、HOME 和开机顺序

原生设置 APK 本来就存在：`/system/priv-app/Settings/Settings.apk`，包名 `com.android.settings`。原来打开被拒绝，是大麦在 ActivityStackSupervisor 中做了系统级拦截。

反编译实机 services.odex 的嵌入 DEX 后确认：当 `hiveview.app.allowsetting=true`，且 Activity 名包含 `com.android.settings`，返回拒绝。属性名与直觉相反：**false 才能打开原生设置**。

```sh
adb shell su -c 'setprop hiveview.app.allowsetting false'
adb shell su -c 'setprop hiveview.app.defaultlaunch me.efesser.flauncher'
adb shell su -c 'setprop hiveview.app.defaultactivity me.efesser.flauncher.MainActivity'
adb shell su -c 'am start -W -a android.settings.SETTINGS'
adb shell input keyevent 3
```

不需要篡改 services.jar。单纯禁用大麦桌面而不修这些属性，HOME 曾触发厂商框架空指针异常。

助手必须声明 SET_TIME_ZONE；本次修复过遗漏权限导致的崩溃。最终版本为 1.2，启动后状态显示“校时成功”。

## 12. Android 5.1 实机兼容坑与收尾

1. **安装 INVALID_URI**：本机 `/data/local/tmp` 为 shell-only 0700，PackageInstaller 的 defcontainer 无法遍历，哪怕 APK 本身是 0644。root 把 APK 临时复制到 `/data/文件.apk`、chmod 0644，再 `pm install -r`，安装后删除临时文件即可。不要因此随便重签 APK。
2. **重启清空 tmp**：重启前把要保留的安装包放 `/sdcard/Download` 或 root-owned 持久备份目录，不依赖 `/data/local/tmp`。
3. **toolbox mv 跨分区失败**：原机 toolbox 的 mv/cp 组合会报 `invalid option -P`；跨 `/system` 与 `/data` 移动目录使用已有 `/system/xbin/busybox mv`，并检查备份完整。
4. **运行中的 APK 不要原地截断覆盖**：先复制到同目录 `.new`，chown/chmod，再同分区原子 rename；PMS 才能可靠重新扫描。对助手还要核对 `dumpsys package` 的版本与新权限，必要时重启。
5. **D8 缓存权限**：曾因 root 启动时 umask 077，把共享 DEX cache 生成成 0600，导致普通 ADB 客户端 Aborted。启动脚本用 umask 022；不要让普通客户端依赖不可读的 root DEX cache。
6. **只读收尾**：修改 `/system` 前 remount rw，完成后 sync/remount ro，并用 mount 确认。如果正在写入或有写 FD 导致 busy，先查明原因，不能默认为成功。
7. **最后复核**：modprobe 恢复 `/sbin/modprobe`，ADB 认证开启，ro.secure/ro.debuggable 恢复，删除 `/mnt/asec` 临时 SUID 和一次性安装/证明脚本，保留恢复备份。
8. **源码签名**：公开仓库源码不含助手签名私钥。重新编译必须自行签名；不同签名不能直接覆盖现有同包名应用。对已改造机器优先使用附带的已签名 APK；若改源码换签名，需先设计数据/系统 APK 恢复路径。
